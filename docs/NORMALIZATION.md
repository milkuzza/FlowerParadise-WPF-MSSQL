# Структура данных и нормализация

Исходные файлы сохранены без изменений в `source-data/`. Для приложения пять исходных Excel-файлов преобразованы в десять связанных отношений. SQL-скрипты и CSV содержат одинаковые данные.

| Таблица | Ключ и назначение |
|---|---|
| roles | PK role_id; уникальные код и название роли |
| users | PK user_id; уникальный login; FK role_id |
| categories | PK category_id; уникальное название |
| subcategories | PK subcategory_id; уникальное название вида цветов |
| manufacturers | PK manufacturer_id; уникальное название поставщика |
| products | PK product_id; FK category_id, subcategory_id, manufacturer_id; уникальная пара name + manufacturer_id |
| sizes | PK size_id; уникальное текстовое значение и порядок сортировки |
| stock_items | PK stock_item_id; уникальная пара product_id + size_id; доступное количество |
| orders | PK order_id; дата и FK customer_id |
| order_items | PK order_item_id; FK order_id, stock_item_id; количество и историческая цена; уникальная пара order_id + stock_item_id |

Атрибуты атомарны. Каждая таблица хранит сведения об одной сущности; неключевые атрибуты зависят от её ключа. Роли, категории, подкатегории и поставщики вынесены в справочники, чтобы их названия не повторялись в каждой строке. Список размеров товара выводится из `stock_items`, а сумма заказа вычисляется по строкам через представление `order_totals` и запросы приложения. ФИО клиента берётся из связанной записи пользователя. Состав товара — текстовое описание из исходного файла, которое не используется как отдельный справочник ингредиентов.

Подкатегории «Розы», «Тюльпаны» и т. п. встречаются в разных категориях: срезанные цветы, букеты и композиции. Поэтому справочник подкатегорий независим от категории, обе ссылки находятся в товаре.

## Сопоставление исходных данных

Товар определяется парой «наименование + поставщик». Две записи «Тюльпаны микс» от разных поставщиков сохранены как два товара. Остатки связываются по этой паре и размеру; строки заказов — по той же товарной позиции. ФИО из Orders_import сопоставлено с фамилией, именем и отчеством из Users_import; все клиенты найдены.

Перед сопоставлением пробелы в текстовых полях приводятся к обычному одиночному пробелу, начальные и конечные пробелы убираются. Это исправляет два расхождения ключей в исходниках:

- У `Лилия «Тигровая»` в Products_import есть конечный пробел, которого нет в остатках и заказах.
- У `Композиция «Гортензия в кашпо»` в Products_import между словами используется неразрывный пробел; в остальных файлах обычный.

Идентификаторы задаются согласованно во всех SQL и CSV. Исходные 10 номеров заказов сохранены. Даты загружаются без изменения; цены преобразуются в целое число копеек без потерь. Отсутствующее изображение хранится как NULL и заменяется заглушкой при отображении.

## Размеры

`sizes.value` имеет тип nvarchar(10), поскольку содержит и длины стеблей (`40`, `50`, `60`, `70`, `80`, `90`), и буквенные размеры (`S`, `M`, `L`, `XL`). `sort_order` обеспечивает правильный порядок внутри размерного ряда. Интерфейс добавляет «см» к числовым значениям. Нулевые остатки сохранены: размер виден в полном размерном ряду, но не предлагается для заказа.

## Деньги и остатки

Цена каталога и цена на момент оформления разделены: последующее изменение каталога или даты заказа не меняет историческую стоимость. Итог — сумма quantity × unit_price_kopecks. Все денежные вычисления используют целые копейки и decimal при отображении.

Stock_Items_import трактуется как снимок уже доступного количества. Исходные заказы повторно не вычитаются из него. При оформлении нового заказа остатки уменьшаются; при удалении заказа или его строки количество возвращается, при редактировании количества учитывается только разница. Эти операции выполняются в транзакциях MSSQL.

Контрольные итоги: 31 товар, 73 позиции, 1 910 единиц в наличии, 20 пользователей, 10 заказов, 31 строка заказа, 133 заказанные единицы, 115 735,00 ₽. Ограничения PRIMARY KEY, FOREIGN KEY, UNIQUE и CHECK обеспечивают целостность внутри базы.
